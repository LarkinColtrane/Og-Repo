# Montreal Residential Market Intelligence

A web application for understanding the Montréal housing market — prices, rents,
inventory, and what they mean for renting, buying, selling and investing.

It is deliberately **not** a listing site. There are no properties for sale here.
The question it answers is *"what is happening in Montréal's residential market,
and what does it mean for me?"*

> ### ⚠️ The market figures are demonstration data
>
> Every statistic in this application is generated by
> [`data/demo/generate.ts`](./data/demo/generate.ts). The numbers are plausible in
> shape — they have realistic seasonality, coherent relationships between prices
> and rents, and several years of monthly history — but they are **invented**.
> None of them came from CMHC, the Ville de Montréal, or any listing service.
>
> The interface says so on every page, and the reason it can say so reliably is
> that the "demo" flag lives in the data layer rather than in a component prop.
>
> The same applies to the **lender rates** on the investor page. The seven
> institutions are real; the rates attached to them are generated by
> [`data/demo/lenders.ts`](./data/demo/lenders.ts), were never published by any of
> those lenders, and nothing was collected from a bank website. Every rate on
> screen is labelled *"Demo rate — not a current lender quote"*.
>
> **The calculators are a different matter.** The mortgage, financing and
> investment arithmetic is real, and correct, regardless of where the market
> figures and rates come from.

## 1. What it does

| Route | What it is |
|---|---|
| `/` | Montréal-wide snapshot: prices, rents, vacancy, inventory, plus a neighbourhood index. |
| `/neighbourhoods` | Every tracked area with its headline figures. |
| `/neighbourhoods/[slug]` | Full dashboard: market overview, rental market, price and rent history, activity, market condition. |
| `/rent` | Rent by unit size, vacancy, history, and comparison against the Montréal average. |
| `/buy` | Prices, inventory and pace by property type, plus a mortgage and affordability calculator. |
| `/sell` | Seller-side indicators and an explanation of what each one does and does not tell you. |
| `/invest` | Financing and returns: down-payment scenarios, a seven-lender comparison, a lender × down-payment matrix, the Government of Canada 5-year bond yield with its mortgage spread, and the full investment analysis. |
| `/compare` | Up to four neighbourhoods side by side. |
| `/property-analyzer` | Address-level analysis — designed, documented, and deliberately not implemented. |
| `/data-sources` | What is connected, what is planned, and under what licence. |

Everything works: navigation, neighbourhood selection, filters, charts, period
selectors, the comparison tool, both calculators, and the API behind them. There
are no decorative buttons.

### Four things it refuses to do

These constraints shaped much of the code, so they are worth stating plainly.

**It does not present generated numbers as real ones.** Provenance is attached to
statistics in the data layer and rendered by one component
([`components/data/source-badge.tsx`](./components/data/source-badge.tsx)). A demo
figure cannot be shown as a live one by forgetting a prop.

**It does not assert market conclusions it has not computed.** The "seller's
market" badge is the output of
[`classifyMarketCondition`](./lib/calculations/market-condition.ts) — four
measured inputs, published weights, and the working shown on screen. The prose
summary on each dashboard is generated from the same numbers
([`summary.ts`](./lib/calculations/summary.ts)), so it cannot drift away from
them. There is no hand-written copy claiming a neighbourhood is hot.

**It does not present a bond yield as a mortgage rate.** The Government of
Canada 5-year yield on the investor page is what lenders pay to borrow, not what
they charge — the page says so, the database says so in a table comment, and the
two data streams share no storage. The spread between them is derived on render,
never stored. See [`docs/BANK_OF_CANADA.md`](./docs/BANK_OF_CANADA.md).

A second real pipeline reads **Ville de Montréal construction permits** from the
city's open-data portal and aggregates them to borough-month totals — the supply
side of a market this platform otherwise describes only through prices and rents.
A borough is not a neighbourhood, and the pipeline is careful about that:
Griffintown and Saint-Henri are both inside Le Sud-Ouest, so a Sud-Ouest figure
appears under both, labelled as a Sud-Ouest figure, with a note naming what else
is in it. [`docs/REAL_DATA_PIPELINE.md`](./docs/REAL_DATA_PIPELINE.md) follows one
number from the portal to the page.

Running the pipelines unattended — shared-secret auth, a provider-neutral
scheduler endpoint, health states and vendor-neutral alerting — is in
[`docs/AUTOMATION.md`](./docs/AUTOMATION.md).

**It does not draw a map it does not have.** With no boundary dataset connected,
the market map renders a labelled schematic grid and says what it is. The GeoJSON
rendering path is implemented and waiting
([`components/maps/`](./components/maps/)) — supply the Ville de Montréal
boundary file and it draws real outlines.

## 4. Installing

Requires **Node 20 or newer**.

```bash
git clone https://github.com/LarkinColtrane/Og-Repo.git
cd Og-Repo
npm install
```

No database, no API keys, no environment file. It runs on the demo dataset out of
the box. `.env.example` documents the variables for later.

## 6. Where the demo data lives

Everything comes from one seed table:
**[`data/demo/neighbourhood-profiles.ts`](./data/demo/neighbourhood-profiles.ts)**.
One entry per neighbourhood — current prices, rents, vacancy, days on market,
dwelling counts, and a growth rate. That is the entirety of the hand-written
numbers.

[`data/demo/generate.ts`](./data/demo/generate.ts) expands those into seven years
of monthly history. Three properties make it usable:

- **Deterministic.** A seeded PRNG, so the same input always produces the same
  series. Server and client never disagree, and nothing flickers between renders.
- **Internally consistent.** Listing and sales volumes are derived from dwelling
  stock; price per square foot tracks median price; year-over-year change is
  measured *off the generated series* rather than authored. A figure the UI calls
  "derived" really is derived.
- **Shaped like real data.** Montréal's resale market has a pronounced spring
  peak and a January trough, and days-on-market moves inversely. Flat synthetic
  lines would teach the wrong lesson about what housing data looks like.

### Adding a neighbourhood

Append one entry to `NEIGHBOURHOOD_SEEDS`. Routes, dashboards, the comparison
table, the map and the API all read from that array — nothing else changes. The
dashboard page pre-renders it at build time via `generateStaticParams`.

Note that `propertyTypes` is per-neighbourhood: Griffintown is condo-only,
because it has effectively no detached houses. The dashboards show an empty state
for the missing types rather than inventing plausible numbers, which is worth
keeping when you add areas of your own.

## 7. How the internal API works

Every route returns the same envelope:

```jsonc
{
  "data": { /* the payload */ },
  "meta": {
    "generatedAt": "2026-06-30T12:00:00.000Z",
    "dataQuality": "demo",          // flips to "live" when a database is connected
    "period": "2026-06",
    "sources": [
      { "sourceId": "src-demo-sales", "sourceName": "Demo sale statistics",
        "updatedAt": "2026-06-30T00:00:00.000Z", "isDemo": true }
    ]
  }
}
```

Errors use `{ "error": { "code", "message" } }` with a matching HTTP status.

| Route | Query parameters |
|---|---|
| `GET /api/market/montreal` | — |
| `GET /api/neighbourhoods` | — |
| `GET /api/neighbourhoods/[slug]` | — |
| `GET /api/neighbourhoods/[slug]/sales` | `propertyType`, `range` (`1y`/`3y`/`5y`), or `from`/`to` |
| `GET /api/neighbourhoods/[slug]/rent` | `bedroomType`, `range`, or `from`/`to` |
| `GET /api/compare` | `slugs` (comma-separated, max 4) |
| `GET /api/data-sources` | — |
| `GET /api/mortgage/lenders` | — |
| `GET /api/mortgage/rates` | `productType`, `termYears`, `lenderId`, `borrowerProfile` |
| `GET /api/mortgage/compare` | `price`, `downPaymentPercent`, `occupancy`, `units`, `termYears`, `amortizationYears`, `productType` |
| `GET /api/market/benchmarks` | `series` (`5y-canada-bond`), `range` (`3m`/`1y`/`3y`/`5y`) |
| `GET /api/civic/permits` | `neighbourhood` or `borough`, `months`, or `from`/`to` |
| `POST /api/internal/market-data/bank-of-canada` 🔒 | Body: `series`, and either `startDate`+`endDate` or `recent` |
| `POST /api/internal/market-data/montreal-permits` 🔒 | Body: `from`, `to`, `maxRecords` — all optional |
| `GET POST /api/internal/market-data/scheduled` 🔒 | `series`, `recent` (default `10`), `notify` — all optional |
| `GET /api/internal/market-data/status` 🔒 | — (pipeline diagnostics) |

🔒 Everything under `/api/internal/` requires
`Authorization: Bearer $MARKET_INGEST_SECRET`, and fails closed in production
when no secret is configured. See
[`docs/AUTOMATION.md`](./docs/AUTOMATION.md).

Query strings are validated with Zod in
[`lib/api/params.ts`](./lib/api/params.ts) before reaching the data layer, so a
malformed request gets a clear `400` rather than a confusing empty result.

### Two ways the UI gets data — and why both

**Server components read the repository directly.** The homepage and the
neighbourhood dashboards call `getRepository()` in the server component. An HTTP
request to your own process would be pure overhead.

**Interactive components fetch the API over HTTP.** Changing the property type on
a price chart issues a real request to
`/api/neighbourhoods/[slug]/sales?propertyType=house&range=3y`. Shipping every
series to the browser up front and filtering in memory would look identical and
teach nothing — and it stops scaling the moment the dataset is real.

Both go through the same repository, so they cannot disagree. Client fetching
goes through the typed client in [`lib/api/client.ts`](./lib/api/client.ts) and
the [`useApiResource`](./lib/hooks/use-api-resource.ts) hook, which handles
loading, error, empty and refreshing states in one place.

## 8. Where PostgreSQL / Supabase connects

At exactly one function.

There are **two** repository interfaces, deliberately separate:
`MarketDataRepository` ([`lib/data/repository.ts`](./lib/data/repository.ts)) for
market statistics, and `MortgageRateRepository`
([`lib/data/mortgage-repository.ts`](./lib/data/mortgage-repository.ts)) for
lender rates. They are different data with different owners, cadences and
licences — rates move daily under commercial terms, statistics move monthly from
public agencies — and they will not become live on the same day. Two interfaces
means either can be switched independently, and each keeps its own
`dataQuality` flag.

The application depends on those interfaces and never on a concrete data source.
For market data, two implementations exist:

- `DemoMarketDataRepository` — reads the generated dataset. Active.
- `PostgresMarketDataRepository` — reads SQL. Written, tested against the schema
  by inspection, not wired up.

[`lib/data/index.ts`](./lib/data/index.ts) chooses:

```ts
export function getRepository(): MarketDataRepository {
  if (!repository) {
    repository = process.env.DATABASE_URL
      ? new PostgresMarketDataRepository(executeSql)
      : new DemoMarketDataRepository();
  }
  return repository;
}
```

That is the whole integration. No page, route, component or type changes — and
`meta.dataQuality` flips to `"live"` on its own, which makes every "Demo data"
badge disappear because they read that flag.

Mortgage rates work the same way, through `getMortgageRateRepository()` and the
same `executeSql` — they are two tables in one database, not two systems.

Full walkthrough, including the ten-line `SqlExecutor`, in
[`docs/DATA_PIPELINE.md`](./docs/DATA_PIPELINE.md) §5 and
[`docs/MORTGAGE_RATE_PIPELINE.md`](./docs/MORTGAGE_RATE_PIPELINE.md) §7. Schema in
[`docs/DATABASE_SCHEMA.md`](./docs/DATABASE_SCHEMA.md),
[`docs/sql/001_initial_schema.sql`](./docs/sql/001_initial_schema.sql) and
[`docs/sql/002_mortgage_rates.sql`](./docs/sql/002_mortgage_rates.sql).

## 9. Replacing demo data with real data

In order — each step makes the next easier:

1. **Apply the schema** to local Postgres or a free Supabase project.
2. **Seed `neighbourhoods` and `data_sources`** from the demo profiles.
3. **Write `executeSql` and flip the factory.** The app now reads Postgres with
   hand-inserted rows and looks identical. That is the proof the abstraction
   holds.
4. **Import one real source.** CMHC's Rental Market Survey is the best first
   target: public, documented, and it maps cleanly onto `rental_market_stats`.
5. **Schedule it, and make failures visible.**
6. **Then** load boundaries, and the map switches to real outlines with no
   component changes.

Sources the platform is designed for, with licences and caveats, are listed on
`/data-sources` and in [`data/demo/sources.ts`](./data/demo/sources.ts): CMHC,
Ville de Montréal Open Data, Données Québec, Statistics Canada, a licensed
listing feed, a licensed rate feed, and the Bank of Canada Valet API.

**For mortgage rates** the route is different, and
[`docs/MORTGAGE_RATE_PIPELINE.md`](./docs/MORTGAGE_RATE_PIPELINE.md) explains why:
do not scrape lender websites. Most prohibit it, posted rates are not the rates
anyone is actually offered, and a markup change silently imports a wrong number.
Licensed aggregators, broker sheets or manual entry are the supported paths. The
Bank of Canada Valet API is free and keyless and is the right place to build the
pipeline muscle first.

## 10. Automating imports with n8n

n8n is a visual workflow tool — a good place to *see* a pipeline before writing
one. A monthly CMHC import:

```
Schedule Trigger  →  HTTP Request   →  Code        →  HTTP Request      →  IF
(0 6 1 * *)          (fetch CSV)       (reshape)      (POST our ingest)    (notify on failure)
```

1. **Schedule Trigger** — cron `0 6 1 * *`. Monthly, because the source is
   monthly.
2. **HTTP Request** — GET the upstream file.
3. **Code** — reshape rows into the JSON the ingest endpoint expects. This node
   is n8n standing in for the transform layer.
4. **HTTP Request** — POST to `/api/internal/import` with
   `Authorization: Bearer $MARKET_INGEST_SECRET`. Batch a few hundred rows per
   request. See [`docs/AUTOMATION.md`](./docs/AUTOMATION.md).
5. **IF** — branch on status and notify yourself on failure. An import that fails
   silently is the same as no import.

The ingest endpoint is not built yet. What it must do — authenticate, validate
with Zod, upsert idempotently, write an `import_runs` row, recalculate
year-over-year — is specified in
[`docs/DATA_PIPELINE.md`](./docs/DATA_PIPELINE.md) §4 and §7, along with
alternatives (Vercel Cron, GitHub Actions) if you would rather not run n8n.

## Learning path

Read the code in this order. Each step depends on the one before it, and stops
being confusing once that one has landed.

### 1. Frontend components
Start with [`components/ui/stat-card.tsx`](./components/ui/stat-card.tsx) — a
component with no data fetching, no state, just props in and markup out. Then
[`card.tsx`](./components/ui/card.tsx) and
[`delta.tsx`](./components/ui/delta.tsx). Notice that `Delta` takes a `polarity`
prop: the component does not assume rising is good, because for a buyer it is
not. That is the recurring idea — components describe, callers decide.

Then [`components/dashboard/market-overview.tsx`](./components/dashboard/market-overview.tsx)
to see primitives composed into a section.

### 2. Data objects
Read [`types/market.ts`](./types/market.ts) top to bottom. These types are the
vocabulary every other layer speaks. Then
[`data/demo/neighbourhood-profiles.ts`](./data/demo/neighbourhood-profiles.ts)
(the seed table) and [`generate.ts`](./data/demo/generate.ts) (how twelve rows
become several thousand).

Then [`lib/data/repository.ts`](./lib/data/repository.ts) — the most important
file in the project. It is an interface with no implementation, and understanding
why it exists is most of what this codebase has to teach.

### 3. API routes
[`app/api/neighbourhoods/route.ts`](./app/api/neighbourhoods/route.ts) is the
simplest: a function, called on a URL, returning JSON. Then
[`app/api/neighbourhoods/[slug]/sales/route.ts`](./app/api/neighbourhoods/%5Bslug%5D/sales/route.ts),
which adds a dynamic segment and validated query parameters.

Run them with `curl` (§5). Seeing JSON in a terminal makes the abstraction
concrete in a way reading cannot.

### 4. HTTP requests
[`lib/api/client.ts`](./lib/api/client.ts) — how the browser calls those routes,
with real error handling. Then
[`lib/hooks/use-api-resource.ts`](./lib/hooks/use-api-resource.ts), which turns a
request into loading, error, empty and refreshing states.

Then [`components/dashboard/price-trends.tsx`](./components/dashboard/price-trends.tsx)
and watch the network tab as you change a filter. Every click is an HTTP request
you can read.

### 5. Database
[`docs/DATABASE_SCHEMA.md`](./docs/DATABASE_SCHEMA.md), then the SQL. Focus on
*why* rather than syntax: why the natural-key `UNIQUE` constraint is what makes
imports safe to re-run, why `NULL` and `0` must never be confused, why the
`data_source_id` foreign key is `NOT NULL`.

Install Postgres, apply the schema, insert a few rows by hand. Then read
[`lib/data/postgres-repository.ts`](./lib/data/postgres-repository.ts) and match
each method to the table it reads.

### 6. External API integration
Pick one source and read its documentation before writing anything. The **Bank
of Canada Valet API** is the best first target of all: free, keyless, well
documented, and it publishes the bond yields that actually drive fixed mortgage
pricing. Then CMHC.

Read [`docs/DATA_PIPELINE.md`](./docs/DATA_PIPELINE.md) §2 — particularly *"things
that reliably go wrong here"* — and
[`docs/MORTGAGE_RATE_PIPELINE.md`](./docs/MORTGAGE_RATE_PIPELINE.md) §1, which
explains why the obvious approach to rates (scraping bank sites) is the wrong
one. Fetching data is easy; joining someone else's names to yours without
silently dropping rows is not.

### 7. n8n automation
Build the workflow from §10 by hand. Run it manually before scheduling it. The
value of n8n at this stage is that each node's output is visible, so a broken
transform is obvious rather than inferred from a stack trace.

### 8. Scheduled imports
Move the workflow onto a cron schedule. Then deliberately break it — point it at
a bad URL — and make sure you find out. This is the step most projects skip, and
the reason so many dashboards quietly show stale numbers.

### 9. Data transformations
Write the transform layer properly in TypeScript, with fixture-based tests:
saved sample upstream rows in, expected typed rows out. This is where a units
error or a mis-joined neighbourhood produces *plausible but wrong* numbers, which
are far worse than an error, because nothing alerts you.

### 10. Creating your own API
By now you have consumed several APIs and built one. Extend it: an ingest
endpoint (§10), then something new — a `/api/property/[address]` route for the
analyzer. Design the response envelope first, write the types, then implement.
That order is the whole lesson.

## Design notes

The interface is built to read like a financial data platform rather than a
realtor site: a restrained neutral palette with a single deep-blue accent,
generous whitespace, hairline borders, tabular figures in columns and
proportional figures in headline numbers, and motion limited to entrances.

The chart palette is a validated colour-blind-safe categorical set, assigned in
fixed slot order and never cycled — a series keeps its colour when others are
toggled. Two of the four light-mode series colours fall below 3:1 contrast on
white, so every chart carries a table view behind a toggle; the data is never
reachable by colour alone. Charts render after mount because their colours depend
on the resolved theme, which the server cannot know.

Dark mode follows the OS by default and can be overridden; the preference is
applied before first paint, so there is no flash.
