# Mortgage rate pipeline

How lender rates get into this application, and what has to be true before they
can be called live.

Right now every rate is generated by
[`data/demo/lenders.ts`](../data/demo/lenders.ts). The institutions are real; the
rates are invented, and the interface says so on every one of them. This document
is the map for replacing them.

---

## 1. The one rule

**Do not scrape lender websites.**

It is the obvious first idea and it is the wrong one, for four reasons that all
bite:

- **Terms of use.** Most Canadian bank sites prohibit automated collection. That
  is a contractual problem, not a technical one, and no amount of rate-limiting
  fixes it.
- **Posted rates are not real rates.** The number on a bank's public page is a
  posted rate. Almost nobody pays it — the discounted rate a borrower is offered
  depends on their file, and it can sit a full point below. A scraper collects
  the wrong number very reliably.
- **It breaks constantly.** A rate rendered by client-side JavaScript into an
  unlabelled `<span>` is a markup change away from silently importing garbage,
  and the failure mode is a plausible-looking wrong number.
- **There is a supported route.** Aggregators already do this collection under
  agreement and license the result. That is the path.

So the pipeline below assumes a **licensed feed** or **manual entry**, not
collection from lender sites.

## 2. The shape of the thing

```
Rate source              Transport              Storage          Serving
───────────              ─────────              ───────          ───────
Licensed aggregator ─┐
Broker rate sheet    ├──►  connector ──► normalize ──► validate ──► PostgreSQL ──► MortgageRateRepository ──► /api/mortgage/* ──► investor page
Manual entry         │     (fetch)       (to our      (reject      (upsert +        (the seam)
Bank of Canada ──────┘                    types)       bad rows)    audit row)
                          ▲
                          │
                    scheduler (n8n / cron) — daily
```

Same five stages as the market pipeline, and deliberately so: one mental model
covers both. What differs is the cadence (daily, not monthly) and the fact that a
stale rate is worse than a missing one.

| Stage | Job | Lives in |
|---|---|---|
| **Connector** | Fetch from one rate source. Knows about HTTP and auth, nothing about our schema. | `lib/pipeline/connectors/rates/` |
| **Normalize** | Map the feed's lender names, products and terms onto ours. | `lib/pipeline/transforms/rates.ts` |
| **Validate** | Reject anything outside a believable band. | `lib/pipeline/validate.ts` |
| **Load** | Upsert into `mortgage_rates`, write an `import_runs` row. | `lib/pipeline/load.ts` |
| **Serve** | `MortgageRateRepository` → `/api/mortgage/*` → the page. | **Already built.** |

The last row is the point: the serving half exists and works. Only the first four
are missing.

### Why rates got their own repository

`MortgageRateRepository` is separate from `MarketDataRepository` rather than more
methods on it. They are different data with different owners, cadences and
licences: rates move daily and come from a commercial feed; market statistics
move monthly and come from public agencies. Folding them together would mean a
rate refresh had to reason about neighbourhoods, and a rate outage would look
like a market-data outage.

It also means each carries its **own** `dataQuality` flag, so the platform can
honestly serve live rates against demo market data — which is the order they will
realistically arrive in.

## 4. Provenance

Every rate row carries the metadata that makes it auditable:

```ts
{
  lenderId:        "rbc",
  productType:     "fixed",
  termYears:       5,
  borrowerProfile: "uninsured",
  rate:            4.90,
  effectiveDate:   "2026-06-15",
  dataSourceId:    "src-demo-mortgage-rates",
  dataQuality:     "demo",          // → "live" when a real feed writes it
  lastUpdated:     "2026-06-15T09:00:00.000Z"
}
```

`dataQuality` is what the UI reads. `RateQualityBadge` renders
"Demo rate — not a current lender quote" for `demo` and a source-and-date line for
`live`. **No component hard-codes the word "demo".** That is the whole mechanism:
the day a feed writes `live`, every badge changes at once, and until then none of
them can be forgotten.

`borrowerProfile` deserves a note. An insured mortgage — under 20% down, with a
default-insurance premium — is *less* risky for the lender and is normally quoted
at a **lower** rate than the uninsured equivalent. Storing one rate per lender
would make every down-payment comparison wrong in the same direction, so the
profile is part of the key.

## 5. Validation

Rates are a small, dense dataset where a single bad value distorts the whole
comparison. The bounds are therefore tight:

```ts
export const mortgageRateSchema = z.object({
  lenderId:        z.string().min(1),
  productType:     z.enum(["fixed", "variable"]),
  termYears:       z.number().int().min(1).max(10),
  borrowerProfile: z.enum(["insured", "uninsured"]),
  // A feed switching from percent to fraction would send 0.0479. Without a
  // floor it imports silently and every payment on the page is wrong.
  rate:            z.number().min(0.5).max(25),
  effectiveDate:   z.string().regex(/^\d{4}-\d{2}-\d{2}$/),
  dataSourceId:    z.string().min(1),
});
```

Two checks worth adding beyond the schema, because they catch the failures a
schema cannot:

- **Movement check.** Reject — or flag for review — a rate that moved more than
  ~150 basis points since the last import for the same key. Real rates do not
  jump that far overnight; a feed change does.
- **Coverage check.** If a source returned fewer lenders than last time, mark the
  run `partial` rather than `success`. A silently shrinking comparison is worse
  than an obvious failure.

## 6. Loading

Same two rules as the market pipeline.

**Idempotent.** The natural key includes `effective_date`, so re-running today's
import updates today's rows while tomorrow's insert new ones:

```sql
INSERT INTO mortgage_rates
  (id, lender_id, product_type, term_years, borrower_profile, rate,
   effective_date, data_source_id, data_quality, import_run_id)
VALUES ($1, $2, $3, $4, $5, $6, $7::date, $8, 'live', $9)
ON CONFLICT (lender_id, product_type, term_years, borrower_profile, effective_date)
DO UPDATE SET rate           = EXCLUDED.rate,
              data_source_id = EXCLUDED.data_source_id,
              data_quality   = EXCLUDED.data_quality,
              import_run_id  = EXCLUDED.import_run_id,
              updated_at     = now();
```

**Audited.** Open an `import_runs` row before fetching, close it after loading,
and only then advance `data_sources.last_updated`. A failed run must not move
that timestamp — otherwise the interface reports rates as fresher than they are,
which is precisely the failure the badge exists to prevent.

Because the table keeps history, nothing is destroyed by a bad import: the
previous day's rows are still there, and `latest_mortgage_rates` is one
`DISTINCT ON` away from the correct current picture once the bad rows are
deleted.

## 7. Turning on PostgreSQL

Two steps, and neither touches a component.

**1. Apply the schema.**

```bash
psql "$DATABASE_URL" -f docs/sql/001_initial_schema.sql   # if not already applied
psql "$DATABASE_URL" -f docs/sql/002_mortgage_rates.sql
```

**2. Flip the factory** in [`lib/data/index.ts`](../lib/data/index.ts):

```ts
export function getMortgageRateRepository(): MortgageRateRepository {
  if (!mortgageRateRepository) {
    mortgageRateRepository = process.env.DATABASE_URL
      ? new PostgresMortgageRateRepository(executeSql)   // same pool as market data
      : new DemoMortgageRateRepository();
  }
  return mortgageRateRepository;
}
```

That is the whole integration. The investor page, the three API routes and every
calculation keep working, and the demo badges disappear on their own because they
read `dataQuality`.

Note the same `executeSql` serves both repositories. Rates and market statistics
are two tables in one database, not two systems — the interfaces are separate so
the *sources* can be switched independently, not because they need separate
connections.

## 8. An n8n workflow

Rates move daily, which makes them a better first automation than the monthly
market data: you find out quickly whether it works.

```
┌──────────────┐   ┌──────────────┐   ┌───────────┐   ┌──────────────┐   ┌─────────┐
│ Schedule     │──►│ HTTP Request │──►│ Code      │──►│ HTTP Request │──►│ IF      │
│ daily 06:00  │   │ rate feed    │   │ normalize │   │ POST ingest  │   │ failed? │
└──────────────┘   └──────────────┘   └───────────┘   └──────────────┘   └────┬────┘
                                                                              │
                                                                              ▼
                                                                        ┌──────────┐
                                                                        │ Notify   │
                                                                        └──────────┘
```

1. **Schedule Trigger** — cron `0 10 * * *` (06:00 Montréal, allowing for UTC).
2. **HTTP Request** — GET the licensed feed, with its key in a header.
3. **Code** — map the feed's lender identifiers onto ours and split each quote
   into insured and uninsured rows. This node is n8n standing in for the
   normalize layer, and it is where the work actually is: no two feeds name
   institutions the same way.
4. **HTTP Request** — `POST /api/internal/rates` with
   `Authorization: Bearer $MARKET_INGEST_SECRET`, the same guard the benchmark
   endpoints already use. See [`AUTOMATION.md`](./AUTOMATION.md) §2.
5. **IF** — branch on the response; notify on failure. A rate import that fails
   silently leaves yesterday's numbers on the page with today's confidence.

The ingest endpoint is not built. It must: authenticate (one line —
`requireIngestAuth(request)`, see [`DATA_PIPELINE.md`](./DATA_PIPELINE.md) §7),
validate with the schema in §5,
upsert per §6, write an `import_runs` row, and return
`{ imported, rejected, runId }`.

### A free API to practise on first

The **Bank of Canada Valet API** needs no key, has clean documentation, and is
already registered as a planned source (`src-boc-valet`). It publishes the policy
rate, conventional mortgage benchmarks and bond yields.

```bash
curl "https://www.bankofcanada.ca/valet/observations/V80691335/json?recent=5"
```

It does not give you lender rates — but it is the right place to build the
connector→normalize→validate→load muscle before touching a paid feed, and the
five-year bond yield it publishes is what actually drives five-year fixed
mortgage pricing. Charting a lender rate against it would be a genuinely useful
next feature.

## 9. Checking the arithmetic without the UI

The comparison is a pure function, so it can be exercised from a terminal:

```bash
curl "localhost:3000/api/mortgage/compare?price=725000&downPaymentPercent=20&occupancy=investment&units=3&termYears=5&amortizationYears=25" | jq '.data.comparison.lenders[] | {lender: .lender.shortName, rate: .rate.rate, monthly: .scenario.payments.monthly}'
```

The investor page computes the same figures in the browser for responsiveness,
but by calling the *same* functions — `compareLenders` and `buildFinancingMatrix`
in [`lib/calculations/financing.ts`](../lib/calculations/financing.ts). One
implementation, two callers. If the endpoint and the page ever disagreed, it
would mean a genuine bug rather than two drifting copies.

## 10. What to build first

1. **Apply `002_mortgage_rates.sql`** and seed the lenders (the file does it).
2. **Flip the factory** and hand-insert a day of rates. The page now runs on
   Postgres and looks identical — that is the proof the abstraction holds.
3. **Write the ingest endpoint**, and drive it with `curl` before any scheduler.
4. **Connect the Bank of Canada Valet API** as a real connector. Free, keyless,
   and it teaches the whole shape.
5. **Then** decide whether a licensed lender feed is worth the agreement.

Do not start at step 5. The expensive part of a data integration is never the
data — it is finding out whether your pipeline notices when it breaks.
